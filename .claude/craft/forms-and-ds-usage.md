# Forms & DS-usage rule (read before building any UI)

Two recurring failures this rulebook exists to stop: (1) hand-rolling markup/classes
instead of the real DS component API, and (2) re-tuning form gaps by hand on every screen.

## The three guards (so it never happens again)

1. **The index** — `DS-COMPONENTS.md` (generated by `node scripts/gen-ds-components.mjs`
   from the `@eidos/ui` barrel) is the authoritative list of every component. Grep it
   FIRST. If a component exists, import it; if not, extend the DS, not the screen.
2. **The hook** — `.claude/hooks/prefer-ds-components.mjs` (PreToolUse) hard-blocks
   hand-rolled DS markup in screens (`className="btn"`, `role="menuitem"`, redefining a
   DS component). Buttons → `<Button>`, menus → `DropdownMenu*`, fields → `<Field>`.
3. **The visual gate** — screenshot the element and compare to its Storybook story /
   migrated DS page. Ship only if it matches.

## DS-first (never freelance a component)

1. **Look up before you build.** For every element, open the DS component source +
   its props (and the gold reference page / story) and use its **real API** — props,
   not invented classes or ad-hoc CSS. Examples that bit us:
   - `DropdownMenuItem` has an **`icon` prop** (`icon={Icons.copy}`) and `variant="destructive"`.
     Passing an icon as a *child* leaves the reserved icon-slot gutter empty **and** glues
     the icon to the label. Always use the `icon` prop.
   - Buttons are the DS `.btn` class API: `ember` (primary), base `.btn` (secondary/filled),
     `outline`, `ghost`, `link`, `destructive`; sizes `lg/sm/xs/icon`. The canonical
     **secondary** is base `.btn` (filled), not `.btn.outline`.
2. **If the DS lacks it, extend the DS — not the screen.** Add the component/token to
   `@eidos/ui` once (see the Field/FormSection/Form primitives below), don't reinvent it per page.
3. **Visual-review gate (mandatory).** After building, screenshot the element and compare
   it to the DS's own rendering of that same component (Storybook / the migrated DS page).
   Ship only if it matches. Alignment/spacing are pixel properties — verify on a screenshot.
4. Route DS-touching work through the `design-system-engineer` agent; verify with
   `contract-verifier` / `eidos:verify`.

## Form spacing standard — ONE source of truth

All form spacing comes from tokens in `packages/ui/styles/tokens.css`. Never hard-code a
field/section gap again — change the token, every form follows.

| Token | Gap | Between |
| --- | --- | --- |
| `--field-label-support` | 2px | label ↔ support text |
| `--field-group-control` | 8px | (label+support) group ↔ control; label-only ↔ control |
| `--field-gap` | 24px | field ↔ field |
| `--form-section-title-body` | 4px | section title ↔ its body |
| `--form-section-gap` | 32px | section ↔ section |

Use the DS primitives (in `packages/ui/src/forms.tsx`, exported from `@eidos/ui`):

- **`<Field label hint action badge required>`** — control-agnostic. Pass any control as
  children (DS `Input`/`Select`, a `RadioCardGroup`, a custom list). Renders `.field`
  (group↔control 8px) with `.field__group` (label↔support 2px); when there's `hint`, the
  `action` rides the support line; with no hint it rides the label line.
- **`<FormSection title description action>`** — `.form-section` (field↔field 24px) with a
  tokenized head (title↔body 4px).
- **`<Form>`** — `.form` (section↔section 32px). Stack `FormSection`s in it for a long form.

`.in-field` (Input/Textarea/Select native) consumes `--field-group-control` too, so DS
inputs match `<Field>` everywhere. Do **not** re-override `.in-field` gap per app.

Rule of thumb: a single-control field → use the DS control's own `label`/`help`. A field
that wraps a non-DS control, or needs support text above the control + an action → `<Field>`.
A multi-section form (create/edit) → `<Form>` of `<FormSection>`s. Then spacing is automatic.
